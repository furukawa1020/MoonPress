# Build the plan you reviewed

MoonPress can refuse to write a different plan from the one you inspected.
The browser's production build requires this check. The CLI exposes the same
native library through `review` and `build-reviewed`:

```sh
moonpress review my-site dist --json > review.json
# Inspect review.json: output actions, digests, dependency changes and exclusions.
review_id="$(jq -r '.report.review_id' review.json)"
moonpress build-reviewed my-site dist "$review_id" --json
```

Keep the report outside the managed output. jq is only a shell example for
reading JSON; the compiler does not depend on it. Without `--json`, `review`
prints the ID and complete plan. A script that immediately approves whatever it
reads does not establish human review. The ID is neither a secret nor authority.

## What is compared

`review_build_plan(input, output, include_drafts=false)` returns
`ReviewedBuildPlan {schema: 1, review_id, plan}`. `plan` is the complete
`DetailedBuildPlan` used by the browser and existing `plan` command. The CLI wraps
it in the existing schema-1 envelope, with command `review` and draft mode.

The review ID is SHA-256 over a versioned, ordered JSON encoding of:

- Exact input and output path spellings and draft mode.
- The complete next manifest, including unchanged artifact dependencies.
- The detailed plan: summary/exclusion events, actions, old/new output digests
  and every dependency delta.

Use the same paths, working directory and draft flag for both commands. Even a
trailing slash changes the identity. `--include-drafts` includes private drafts;
use a separate preview directory. Review is read-only and holds a shared output
parent lock only while inspecting; it creates no approval or lock files.

`compile_reviewed_site` acquires the exclusive output lock, loads and validates
output ownership, computes the current plan once, and compares its ID. A mismatch
fails before publication. A match applies that exact in-memory plan, rather
than rerunning a build that could compute something different. JSON success for
`build-reviewed` contains the ordinary `BuildReport`; it equals the reviewed
plan's summary. CLI operation errors exit 1 with empty stdout and stderr detail;
incorrect arguments exit 2. Each optional flag may appear once in either order.

## Changes that require another review

Changed output bytes, a missing owned output, a deletion, a draft-mode change,
or a changed dependency with identical generated bytes all change the plan.
After a successful changing build, replaying its old ID is rejected: the next
plan is now a no-op. An unchanged no-op review can be reused; this is a state
comparison, not a single-use token, approval ledger or stored snapshot. Edits
outside the compiled plan (for example the body of an excluded draft) need not
change the ID. It does not fingerprint every file in the project directory.

The browser presents the build form only after inspection. Missing/invalid/stale
IDs fail; the error page offers reinspection. Reinspection never submits a build
automatically. Ordinary CLI `build` remains an explicit unreviewed operation.

## Boundaries

This is for trusted local projects and cooperative MoonPress writers on the
tested Linux filesystem. Source files are not locked or read as an atomic
filesystem snapshot. The plan binds the bytes and dependencies observed by the
planner; it does not promise that source files remain unchanged afterwards.
Foreign files, manual output edits and symlinks remain errors even with a matching
review ID. An external process ignoring locks or changing paths concurrently is
outside the contract. Hashes do not authenticate projects or reviewers.

Publication retains the existing staging, rollback and recovery behavior and
[power-loss limitations](publication.md). This check does not make directory
publication atomic. It creates local output, makes no hosting request and cannot
prove which files a host serves. Existing Actions deployment rebuilds from its
selected commit; it does not consume a local browser review ID.

The API, CLI, HTTP and transition suites exercise read-only inspection, exact
report/clean-build parity, same-byte dependency changes, restoration, deletion,
stale replay, ownership checks and a real process paused under the exclusive
lock while its source changes.
