# Security and capacity targets

MoonPress aims to exceed dynamic WordPress delivery without weakening the CMS
editing boundary. Feature compatibility remains tracked in wordpress-parity.md;
this target is not a claim of complete WordPress plugin/runtime compatibility.

Public delivery consists of generated bytes served by a static origin/CDN.
There is no public MoonPress login, PHP interpreter, database, write API, or
plugin execution endpoint in that architecture. Keep source content, local
configuration, history, trash, build journals and tokens off the public origin.
Use `scripts/prepare-pages.sh` or the verified ZIP export to publish only reviewed,
owned artifacts; do not serve the site source or a parent of it. An operator's
trusted layouts and assets still require review. Static hosting can still suffer
misconfiguration, malicious content, dependency compromise and volumetric attacks.

The admin and preview listeners bind loopback only. They are sequential local
editing tools, not production traffic servers. Headers are capped at 16 KiB,
ordinary bodies at 256 KiB, multipart uploads at 8 MiB. One absolute five-second
monotonic read deadline covers headers and body; trickled bytes do not renew it.
Responses have their own bounded write deadline. Local untrusted processes can
still consume time on these listeners; do not expose them through a reverse proxy.
CSRF tokens, exact Host/Origin checks, restrictive CSP, versioned edits, retained
directory descriptors and guarded output publication remain required safeguards.

Security acceptance is based on adversarial checks, not vulnerability-count
comparisons: traversal/symlink races, stale writes, hostile markup, CSRF/framing,
size/time limits, interrupted writes and unintended publication. Existing native,
socket and real-browser tests exercise these boundaries. No independent penetration
test, exhaustive audit or denial-of-service immunity is claimed.

Performance acceptance includes useful work and errors: successful response
identity, full-response median/p95/p99, valid requests/second and error rate at
specified concurrency. The WordPress benchmark now runs a bounded NGINX/FPM
comparison alongside its serial and native-build measurements. Cached WordPress
is a required control: both products can benefit from static caching and CDNs.
Never use the serial PHP development server numbers as production capacity.

For a production capacity decision, repeat on the actual origin and representative
articles/assets, with a separate load host, realistic connections/TLS/cache-hit
mix, fixed arrival-rate steps and a sustained soak. Declare a latency/error SLO
before measuring. Track origin CPU, resident memory, network egress, open sockets,
CDN hit rate and upstream/database pressure. Report the highest tested rate that
meets that SLO, with headroom; account for shared-client bottlenecks and tail
latencies rather than extrapolating an unlimited visitor count.

References: [WordPress hardening](https://developer.wordpress.org/advanced-administration/security/hardening/),
[NGINX request limiting](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html).
Rate limits must use the real client address only behind explicitly trusted
proxies; a client-supplied forwarding header is not an identity boundary.
