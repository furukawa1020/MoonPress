# 初めての記事を公開するまで

対応環境はLinux x86_64です。[README](../README.md#quick-start)の手順で実行ファイルを構築し、サイトを初期化して管理画面を起動してください。別の版のMoonBitがある場合は[専用の導入先](toolchain.md)を指定します。MoonBit不要の[Linux用試用パッケージ](native-package.md)も配布しています。解凍後の START-HERE-ja.txt と RECOVERY.txt を参照してください。安定版配布やmacOS/Windowsの動作確認はまだ完了していません。

ブラウザで **http://127.0.0.1:8080/rooms** を開きます。作業中は起動したターミナルを開いたままにし、終了するときはCtrl-Cを押します。管理画面とプレビューに隣り合う2ポート（標準8080・8081）を使うので、両方が空いている必要があります。

1. **Write and save**：Create a draftからタイトルとファイル名（例：first-post）を入力し、Markdown本文を書いてSave articleで保存します。画像はMediaからアップロードし、表示されたMarkdownを本文に貼ります。
2. **Preview your saved drafts**：Build full preview filesでテーマ・画像を含むプレビューを生成します。上部の **Open built preview** を押すと別タブ（標準では http://127.0.0.1:8081/ ）で開き、画像・CSS・ページ間リンクを確認できます。ここには保存済み下書きが含まれます。編集後は再ビルドしてブラウザを再読み込みしてください。
3. **Choose what goes live**：公開する記事を開き、保存後にSet ready for buildを押します。Draftは下書き、Readyは通常ビルドに含める状態です。
4. **Review before building**：Inspect production changesで追加・変更・削除と、その原因となる元記事・レイアウト・設定などの依存関係を確認します。エラーが出た場合は表示された元ファイルや出力の問題を直してから再確認します。手動編集した生成物は上書きされません。
5. **Create production files**：確認結果の画面にあるBuild production filesで `.moonpress-build` に下書きを除く公開用ファイルを生成します。確認後に変更計画が変わると書き出さず停止するので、再度Inspect production changesで確認してください。プレビュー用ディレクトリとは分かれています。
6. **Publish and verify**：上部の **Publish** で本番出力が最新かを確認します。Build neededなら差分確認とビルドをやり直し、エラーがあれば修正します。公開用ファイルをホストへ配置するか、設定済みのGitHub Actionsで保存済みソースをビルド・公開します。[GitHub Pages設定](deployment.md)には一度だけ管理者の操作が必要です。Actionsの成功と実際の公開URLを確認してください。

保存・Readyへの変更・ローカルビルドだけではインターネットに公開されません。この管理画面はホストの公開状態を取得していません。記事をDraftに戻した場合も、通常ビルドをやり直してホストへ反映するまで公開済みページは残ります。

記事のURLを変更する前には、編集画面の **Inspect saved article references** で参照元と参照先を確認できます。必要なら **Include saved drafts** で下書きも含めます。記事の参照元は編集画面へ戻るリンクになっています。CSS・外部URL・自動生成された一覧リンクなどは対象外なので、参照ゼロは削除してよいという保証ではありません。リンク切れのある範囲はエラーとして表示されます。[参照範囲の詳細](references.md)。

MoonPressの実装はMoonBitのnative実行ファイルと薄いC境界です。管理画面はHTMLフォームで操作でき、JS/TS/Nodeは不要です。編集・CLI・管理画面で共通の型と検証を使い、元ファイルの依存関係から変更理由を追跡します。MoonBitだけに可能な機能という主張や、他製品より速いという未測定の主張はしません。

全体から調べる場合は、管理画面の **Output references** または `moonpress reference-summary site` を使います。画像・アーカイブ・リダイレクトも含む出力一覧から、参照の根拠を開けます。Incoming / Outgoing は自己参照を含む辺の数、Self は自己参照、Other referring outputs は自分以外の参照元出力の数です。同じ記事から2種類のURLでリンクされても参照元は1件です。下書きを含める範囲は明示的に切り替えてください。

画像や添付ファイルを同じURLで更新するには、**Media → Replace this media at the same URL** を選び、新しいファイルを指定します。画面を開いた後に元ファイルが変更されていれば上書きを拒否します。失敗時は **Reload current media version** で現状を確認してから選び直してください。差し替えは保存済み素材だけを変更するので、その後にビルド内容をレビューして生成・配信します。元に戻すためのバックアップは別途保存してください。

## サイト設定の変更

管理画面の **Site settings** で `site.json` を編集できます。設定がない場合の
新規作成と、不正なJSONの修復にも対応しています。保存時には読み込み時の
バージョンを照合し、競合した場合は入力内容と元のバージョンを保持します。
Reloadで現在の内容を読み直し、比較してから再編集してください。

保存が確認するのは設定項目の形式だけです。レイアウトやリダイレクト先を含む
サイト全体のチェック、プレビュー、本番差分の確認、ビルドは別に実行します。
保存だけで公開用出力やホスティングは更新されません。CLIからは
`settings-read` / `settings-save` を使えます。[詳細](site-settings.md)。

画像をアップロードすると、Media一覧と置き換え画面でPNG・JPEG・GIF・WebP
（8 MiBまで）の保存済み画像を確認できます。画像を置き換えたら画面を再読込
してください。古いURLは新しい画像に自動で切り替わりません。画像を見るだけ
ではサイトは再ビルドされないため、サイト全体への反映はプレビューを再ビルド
して確認します。SVGなど他形式は記事への挿入用リンクとして扱います。

## 公開用ZIPをダウンロードする

本番ビルド後に **Publish → Download production ZIP** を押すと、検証済みの
HTML・CSS・公開アセット・`.nojekyll` をまとめて取得できます。下書き、ソース、
管理用の `.moonpress.json` は入りません。上限はZIP全体64 MiB・10000ファイルです。
ボタンがない場合は本番ビルドを行ってください。表示後に保存内容が変わると
ダウンロードは拒否されるため、再度レビュー・ビルド・Publish確認を行います。

通常はZIPを展開し、その中身をホストの手順に従って配置します。削除した記事も
ホスト側から除去してください。ダウンロード成功は公開完了を意味しません。
実際のURLでページ・画像・CSS・削除済みURLを確認します。
CLIの使い方と制限は [ZIP書き出し](site-export.md) を参照してください。

## 不要な画像・添付を削除する

**Media → Review removal** で削除前に確認します。下書きやテンプレートに
参照が残っていると削除できません。参照元を直してから、もう一度確認してください。
CSS・対応していないHTML・外部サイトからの利用は検出範囲外なので、自分で確認します。

削除するファイル名を確認し、必要なら先にバックアップを取ります。確認チェックを
入れて **Remove this media permanently** を押すと、ローカルの元ファイルを削除します。
取り消し機能はありません。確認後に画像や記事が変わった場合は、古い確認IDでの削除を拒否します。

生成済みプレビュー・本番出力・公開済みのコピーは、この操作だけでは消えません。
プレビューを再生成し、本番の変更をレビュー・ビルドして、ホストにも削除を反映してください。
詳細は [メディア削除の仕様](media-removal.md) を参照してください。

### ビルドが途中で止まった場合

管理画面の公開準備でエラーになったら「inspect production recovery」から
本番出力の復旧診断を開けます。この画面はファイルを変更しません。
ターミナルでは次の順で確認・復旧します（パスは自分のサイトに合わせます）。

```sh
moonpress recovery-plan 'my-site/.moonpress-build' --json
moonpress recover 'my-site/.moonpress-build' --json
```

`recovery-plan` の `rolled_back` / `finalized` は実行予定であり、まだ復旧していません。
`recover` がその時点の状態を再検証します。成功したら再び本番ビルドをレビューしてください。
不完全なジャーナル、手動変更された出力、不明なファイルは自動復旧できません。
新しいビルドは出力やステージング領域を作る前に、出力の親ディレクトリへ
完全な復旧記録を保存し、最後の後片付けまで保持します。準備中や後片付け中の
プロセス強制終了を含む復旧試験を実施しています。出力と同じ親にある
`.moonpress-recovery-*.json` を削除・移動せず、出力の名前も変えないでください。
旧版の不完全な記録は引き続き復旧できません。Linux の `O_TMPFILE`、
`/proc/self/fd`、ハードリンク、親ディレクトリへの書き込み権限が必要です。
電源断やディスク故障に対する永続性は保証していません。
この機能は記事編集の取り消しやホスティング先の復旧ではありません。

## おへやの道案内と保存途中のデータ

入口は保存状態から次の行き先を提案します。下書きは残したまま、公開対象だけを
もちだすこともできます。ぷれびゅ〜る〜むには「未生成・最新・再生成が必要・確認不可」
の状態が表示されます。「プレビューをつくる」「変更計画をみる」「公開用ZIPをダウンロード」
から操作します。従来の英語の手順は `/workflow` でも開けます。

保存に失敗した場合は、再読み込み前に画面の入力内容をコピーしてください。
上部の「編集データの案内所」(`/authoring-recovery`) では、保存用ステージの場所・サイズ・
SHA-256と救出コマンドを確認できます。画面を開くだけでは書き込みません。
バックアップ先はサイトの外に指定し、救出した内容は確認してから必要な部分を戻します。
未送信のブラウザ入力は救出できません。上限8 MiBを超えるファイルはそのまま保管します。
